# MCP Task Orchestrator

> Maintenance rule: this file holds only what scanning the code will not tell you quickly - traps, guard rules and their tests, where things live, and the session layers. No defaults, counts, version numbers, history or detail a named file already states: point at that file instead.

A Kotlin MCP server for hierarchical work items with dependencies, note schemas and gated phase transitions.

## Domains and responsibilities

Task Orchestrator mechanics and process are separate domains. The plugin encodes how Task Orchestrator works and ships generic engineering skills as defaults; a project's process lives in config it can override (note schemas with `guidance` and `skill:`/`skillPointer`, seat `skills:`, traits, served rules, run-profile, `dispatch-policy.json`). Only the schema defines the workflow's structure: which types, phases, notes and seats exist and in what order. A rule governs a seat's conduct inside that workflow.

| Layer | Holds | Never holds |
|-------|-------|-------------|
| Plugin mechanics: skills, agents, workflows and hook text (`claude-plugins/task-orchestrator/`), engineering skills excepted | Task Orchestrator mechanics (tools, phases, gates, runs, seats, dispatch, hooks); host integration (Agent `model`/`effort`, ToolSearch, plan mode, `AskUserQuestion`); pointers to rules and schema fields | A named Claude Code or Anthropic skill; a project's paths, commands or conventions; process steps a project could choose differently |
| Plugin engineering skills (the `claude-plugins/task-orchestrator/skills/` directories that carry generic engineering practice rather than Task Orchestrator mechanics, whether or not `claude-plugins/task-orchestrator/hooks/lib/seat-skill-defaults.json` names them as a seat default) | Generic engineering practice for a seat's work (planning, implementing, reviewing, test authoring) or for an engineering task a user runs (auditing code, keeping a glossary), overridable per project through seat or note skill binding (a seat's `skills:`, a note's `skill:`) | Anything specific to one repo; a named Claude Code or Anthropic skill |
| Bundled rules (`claude-plugins/task-orchestrator/bundled-rules/`) | Generic process defaults: defaults for a seat's conduct, overridable per project | Anything specific to one repo |
| Project config and rules (`.taskorchestrator/`) | This project's process: schemas, traits, rules, run-profile, and the Claude Code skills a note's `skill:` or a seat's `skills:` points to | - |
| Project skills (`.claude/skills/`) | Repo mechanics (release, Gradle lock, migrations, deploy), and the skills a note's `skill:` or a seat's `skills:` points to | Copies of rules or schema guidance; decisions the schema makes (which notes exist, which phases are reviewed) |

A Claude Code or project skill is reached only through a seat's `skills:` or a note's `skill:` (or `skillPointer`), never named in plugin or orchestration-skill prose; the plugin's own engineering skills reach a seat as its defaults. A process change goes to the layer that owns it: schema (the workflow's structure), rule (a seat's conduct) or run-profile first; skill or plugin text only for mechanics or generic engineering practice. The guard test that enforces this boundary is `claude-plugins/task-orchestrator/hooks/tests/contract-domain-boundary.test.mjs`.

The layer table says where text lives; the concept table below says what kind of statement each concept may make. A sentence belongs to exactly one concept, and no concept is described in terms of another. In the layer table, the plugin's mechanics skills sit in the plugin mechanics row and its engineering skills in the plugin engineering skills row.

| Concept | Holds | Never holds |
|---------|-------|-------------|
| Mechanics skill (tool usage) | How Task Orchestrator works: tools, phases, gates, runs, seats, dispatch; how to read a schema and act on what it says | What a project's workflow should be; engineering craft |
| Engineering skill | How to do one seat's work well: knowledge, criteria, method; it may order the work inside its own craft | Tool mechanics (phases, gates, seats, hand-offs, hooks); when it is loaded or who checks it |
| Rule | A short must-do for a seat's conduct | Engineering depth; workflow |
| Schema | The workflow: which types, phases, notes and seats exist, their order, and which skill or rule is bound to which seat or note | How to do the work; enforcement |
| Hook | Timing and enforcement in the client: hint, record, refuse; it reads what the schema says | Engineering content; workflow decisions |
| Server | State and gates: a note exists, a seat owns it, a transition is allowed; the tool contract: what each tool and parameter does and when to call it | Engineering craft; a project's workflow decisions |

Binding is a schema concept with two sources: the project's schema and, where the schema is silent, the plugin's defaults table, which is data only (a seat to names), never prose in a skill or a hook; a declared list always replaces that table. A seat's rule keys come in three classes, from one plugin table (`claude-plugins/task-orchestrator/hooks/lib/seat-rules.json`): a protocol rule, which the tool's own machinery breaks without, is tool mechanics outside binding, chosen by the plugin by the seat's role; a plugin-chosen rule is one the plugin adds for a role whatever the schema says (`commit-discipline` for a writing seat: one shared index, and verify reads its commit form); a seat default applies only where the seat declares no `rules` list, which replaces it (`review-scoping` is one). No schema or declared list removes a protocol or plugin-chosen rule, and a declared protocol key of another role is dropped and reported. A project may replace a protocol rule's text, and its copy then stops receiving plugin updates; conduct for a seat is added with a project rule on the seat's `rules` list. Note guidance says what a note must record and in what shape; how to do the work belongs in the skill bound to the note or seat.

Test for a sentence: it says what good work is or how a seat goes about its craft (engineering skill); it explains how to use the tools to run the work (mechanics skill); it says what one tool or parameter does or when to call it (server, in the tool contract); it says which phases, notes or seats exist, their order, or what is bound to what (schema); it is a short must-do on any project using the seat (rule); it says when something is hinted, checked or blocked (hook, in code).

Example, test blindness: how to derive a test's expected result from the specification rather than from the code is an engineering skill; that the test plan is a queue note the planner seat fills, so it exists before any implementation, is the schema; when that skill is hinted, or a note write made without it is refused, belongs to a hook.

## Rules a guard test enforces

Tests are under `current/src/test/kotlin/io/github/jpicklyk/mcptask/current/`. Of the ratchet baselines under `current/src/test/resources/architecture/`, the layering, package-cycle and dialect-neutrality ones are empty, so any violation of those rules fails; in every baseline a line that no longer matches fails too. Fix the code; never add a baseline line.

- **Layering** (`architecture/LayeringTest`, rules R1-R5 in `LayeringRules.kt`): `domain` and `model` (the shared model) -> `application` -> `infrastructure` -> `interfaces`, an outer layer may depend on an inner one, never the reverse. `infrastructure -> application` is allowed (adapters implement application ports). A `platform/` folder counts as the layer it came from (the table in `LayeringRules.kt`), and a `platform/` folder missing from that table is a violation. A slice is a first folder that is not a legacy layer or shared area (the reserved list is `RESERVED_FIRST_SEGMENTS` in `architecture/GuardSupport.kt`): `<s>/F.kt` is its top package (what another slice or the platform names), `<s>/internal/{domain,app,sqlite,wire}/` count as `domain`, `application`, `infrastructure` and `interfaces`, and any other path under `<s>/` is a violation (slice shape). `domain` and `application` must not import `io.modelcontextprotocol` or `io.ktor`. No layer may import `bootstrap`.
- **Application package cycles** (`architecture/PackageCycleTest`): the `application/<sub>` packages are acyclic; slices are out of its scope (`SliceGraphReportTest` only reports slice cycles, report-only; the step-9 rule S2 will enforce them). To share a type, move it down to a package every consumer already sits above.
- **Dialect neutrality** (`architecture/DialectNeutralityTest`): `org.sqlite.*` and `org.jetbrains.exposed.*`, and SQLite tokens such as `PRAGMA` or `datetime(` in string literals, appear only under `infrastructure/sqlite/`, `platform/sqlite/` and a slice's `<s>/internal/sqlite/`. Storage ports (`*Store`) live in `application/port/`, except `EventStore` and `IdempotencyStore`, which live in `platform/port/`, and a slice's own ports, which may sit in its top package or `internal/app/`.
- **Environment access** (`architecture/EnvAccessTest`): `System.getenv` only in `AppConfig.kt`, `EnvBoolean.kt` and `LogFileAppenderInstaller.kt`; everything else receives a typed value from the composition root; a test never calls `AppConfig.fromEnv()` without a resolver (pass `{ null }` or a map lookup).
- **Flyway is the only schema path** (`architecture/NoSchemaUtilsInProductionTest`): a new table or column starts with a migration. Released migration files are byte-immutable (Flyway checksums every line, comments included). The Exposed table objects must match the DDL and the compiler does not check it: `SchemaParityTest` and the snapshots in `current/src/test/resources/schema/snapshot/` do, so a schema change edits the migration, the Exposed object and the snapshot together.
- **Tool parameters are documented once**, in the `@Doc` of the request-class field; a tool `description` or select/op `doc` covers only operation choice, triggers, gates and cross-field constraints. After a `@Doc` edit run and commit both `./gradlew :current:regenerateToolGoldens` and `./gradlew :current:regenerateApiReference` (`ToolSchemaGoldenTest`, `ApiReferenceFreshnessTest`, `ToolSurfaceGuardsTest` check it). Checklists for a new tool, op, migration or dependency: `.claude/skills/add-component/SKILL.md`.
- **Domain boundary** (`claude-plugins/task-orchestrator/hooks/tests/contract-domain-boundary.test.mjs`, library `scanDomainBoundary` in `claude-plugins/task-orchestrator/scripts/lib/contract-checks.mjs`): the whole plugin tree (tests and gitignored files excluded) never names a Claude Code or Anthropic skill, a project skill or a project command in slash form (`/name`), nor, for a hyphenated name or `simplify`, in skill form (`name skill`, `skill: name`), and never says "this repo"; project skills are scanned for undeclared host skills. Not checked: bare-word mentions, paths, conventions, process steps, and whether a baseline row's owner item is still open. Rows live in `claude-plugins/task-orchestrator/scripts/lib/domain-boundary-allowlist.json` (host integration and labelled examples, per file and name) and `claude-plugins/task-orchestrator/scripts/lib/domain-boundary-baseline.json` (each row names its owning item and gap; the baseline is empty); a row whose hit is gone fails. A plugin skill directory removes its own name from the scanned names, so a test fails when a new one shares a name with a host skill, a project skill or a project command. Fix the text; never add a baseline row.
- **Test functions** need a block body or an explicit `: Unit`; JUnit 5 silently skips a non-void test (`architecture/TestFunctionReturnTypeTest`).

## Config traps

- **Runtime config is DB-only.** `.taskorchestrator/config.yaml` under `AGENT_CONFIG_DIR` (default: the working directory) is imported into the DB at every boot by the `server-config-import` data step; the server then reads the stored head per call, so editing the file does nothing until a restart, and a version appended by another process on a shared volume is served without one.
- **Two configs, two delivery paths.** The global floor mounted into the container is `deploy/global-config/.taskorchestrator/` (process schemas shared by every project). This repo's own `.taskorchestrator/config.yaml` is dogfood project config, pushed per root by the plugin's `config-sync` SessionStart hook; it is never mounted.
- **Boolean env vars** go through `EnvBoolean`: most fall back to the default with a WARN on an unrecognized value, but `API_ENABLED`, `API_ALLOW_UNAUTHENTICATED`, `MCP_ALLOW_UNAUTHENTICATED` and `API_JWKS_ALLOW_INSECURE_URL` fail startup. `RESOURCE_LEASES_ENFORCED` is read once at startup; changing it needs a restart.
- **Single construction sites.** Production constructs `ToolExecutionContext` once, in `ServerComposition.build()`, and `AdvanceService` once, in `AdvanceServiceFactory.forItem()`. A new constructor parameter given a default value compiles without being passed there, so wire it at that site by hand.

## Session Layers: Orchestrator and Director

Terms (seat, orchestrator, director, session mode, board, decision, escalation, orchestrator placement) are defined in [GLOSSARY.md](GLOSSARY.md); this section holds only the rules and reasons around them.

**Why.** One session used to be both the user's contact and the driver of every run. Its context filled, it was unavailable while a run was in flight, and held state was fragile across compaction. The layers keep driving the work apart from deciding, and let a run's orchestrator be a disposable agent. Each context stays purposeful and clearable, token cost stays proportional to the work, and the server (not a prompt) holds state and boundaries.

**Why a director:** (1) a lean, long-lived context; (2) one decision inbox across runs; (3) the user-facing session stays free while work runs in the background; (4) more parallelism and longer-running work than one session can hold. Small work or one short wave does not need it: orchestration mode is enough, and a director adds a layer and its cost.

**Rules across the layers** (judge any change to director, orchestrator or run-wave behaviour against these):

- **Altitude.** The director never opens a file or reads a diff, test output or note body, except one decision request and a run rollup. It hands every other read and edit to a run's orchestrator or a background agent, which returns a concise result. Director mode runs on the same connection and tools as the orchestrator, and the `director-guard` hook is the one place altitude is enforced: it denies body reads and edits, and allows read-only scripts and background dispatch. The director tool profile (no read that returns a body) and the hardened director agent stay available as optional extra limits; the code still treats them as the default entry and has not changed yet.
- **Content flows down, pointers flow up.** A layer hands the one above ids, counts and short reasons, never note bodies, diffs or transcripts. Notes are the report.
- **Server records are the state; messages are wake-ups.** Every layer restarts from server state (runs, seats, decisions, notes) plus its run files; nothing needed to resume lives only in a conversation. A run's orchestrator may be a disposable background agent for that reason: it resumes from the run view and its run files, never from conversation.
- **Driving and deciding stay apart.** A seat or an orchestrator raises a decision; the user or the director answers it, as the decision class allows. An orchestrator never answers one itself. In orchestration mode it records the user's own words as the rationale. A PreToolUse hook denies a subagent's `runs_write` `answer`, `ack`, `pause` or `resume`. An answer never resumes the item: the orchestrator does, inside a run or outside one.
- **Identity is declared.** The director is a call with no seat token. A run's orchestrator holds the run token (`RunPermissions`); in code that token and its pseudo-seat still carry the old name (`coordinatorToken`, `RunSeat.COORDINATOR`). The director path is not a security boundary, since any credential with the capability may call it: put decision authority in a credential's capabilities and scope.
- **Cost is measured, not self-reported.** Model and effort come from `dispatch-policy.json` per class of work, and every dispatch names both. Token cost is read from Claude Code transcripts after a run into `delegation-metadata`; the session retrospective analyses it and reports the share of the session's token volume (by meter and model) that notes record; the tool holds no prices.

Key files (plugin paths under `claude-plugins/task-orchestrator/`): `skills/director/SKILL.md` and `hooks/director-guard.mjs` (director mode); `skills/director/references/coordinator-tiers.md` and `scripts/coordinator-tiers.mjs` (orchestrator placement); `skills/run-wave/SKILL.md`; `scripts/lib/meters.mjs` and `skills/session-retrospective/SKILL.md` (cost); server side `interfaces/shared/tools/runs/RunPermissions.kt` and `platform/tool/ToolProfile.kt`; user-facing chapter 12 of [current/docs/workflow-guide.md](current/docs/workflow-guide.md).

## Build and run

```bash
docker build -t task-orchestrator:dev .
docker run --rm -i \
  -v mcp-task-data:/app/data \
  -v "$(pwd)"/deploy/global-config/.taskorchestrator:/project/.taskorchestrator:ro \
  -e AGENT_CONFIG_DIR=/project \
  task-orchestrator:dev
```

Name Node test commands by file path or glob (`node --test path/to/*.test.mjs`), never by directory: Node 22 on Windows reads a directory argument as a module and fails.

Never pipe `./gradlew` output to `tail`; run it directly and read the full output. Compiler warnings fail the build, main and test alike (`allWarningsAsErrors` in `current/build.gradle.kts`): fix the warning, or silence it at its site with a one-line reason. Tests use JUnit 5, MockK and a real file-backed SQLite fixture (`SqliteTestDatabase`).

## Git workflow

- The PR boundary is the planned scope: one approved plan is one parent feature and one PR; its waves run inside it on the shared `feat/<slug>` worktree branch with no PR between them, and a plan splits into several parents only where its `work-breakdown` note names a reason. One PR opens once every child is terminal, and the parent completes after that PR is `MERGED`; a Direct or Delegated item gets its own branch and PR and completes after it merges. Procedure: the `implement` skill (`.claude/skills/implement/SKILL.md`, then `wave.md`, `direct.md` or `delegated.md`).
- Conventional commits referencing the issue; all tests pass before a commit; never force-push `main`.
- Merge strategy follows the PR's shape. Squash is the default: a single-item (Direct or Delegated) PR, a fix, docs or chore branch, and any branch whose commits carry review churn. A merge commit is for a Parallel-tier feature branch whose own commits (the first-parent chain) all have conventional, item-tagged subjects, fix-seat commits and a base-merge commit included; any other subject makes it a squash. Never rebase a branch to qualify: notes and run files record its SHAs. The test is the `implement` skill's "Merge method". Rebase-merge is disabled. The repo titles both merge and squash commits with the PR title, so a PR title is a conventional-commit subject.
- After a merge: `git checkout main && git pull origin main && git branch -D <branch>`.
