# Plugin hooks

Hook entrypoints live in this directory and are wired by `hooks-config.json`. Shared plumbing lives in `lib/`;
every module is pure at import (no top-level I/O) and never throws.

## Hooks on the envelope

The write-path hooks read the 4.0 contract, not the 3.x one. `phase-guard-record` (PostToolUse `advance` and `items_read`) and
`dispatch-hint` parse `tool_response` with `parseToolResult` and read every `results[i]`: an element is recordable when
`ok` with a `newRole` (`gate_blocked` records nothing: it means a note is missing). A phase-owner seat (`implementer` or
`reviewer`) already in its phase sends no `start`, so its first item-mode context read is recorded instead, when the
item's role is the one the seat owns and nothing is recorded yet; a non-empty top-level `seatToken` marks a run seat,
which is never recorded. A 3.x-shaped result records and hints
nothing and shows the legacy-shape warning once per session. `phase-guard` (SubagentStop) reads each recorded item's
gate with `items_read` `select: "context"` (`POST /api/v1/ops/items_read`) and skips `workflow-subagent`. It blocks a stopping seat only on that seat's own missing notes: when the gate carries `missingBySeat` and the view's `seats` names the stopping seat, only `missingBySeat[seat]` counts (the `unowned` bucket and other seats' keys never block); otherwise it falls back to the flat `missing` list minus the test-author-owned keys (kept when the stopping seat is the test author). When a block hint would name the gate's `skillPointer`, it reads the root's served rule keys once (`config` op `rules`, shared session marker, read capability) and hints a pointer that is a served rule key as a rule to fetch.
`skill-enforcement` (PreToolUse `notes_write`) acts on `ops[]` elements with `op: "upsert"` and takes skill and
`maxLength` facts from the server: one `config` `effective` read per session, cached in a session marker, and the
item's `items_read` `schema` view per op. A note skill that is a served rule key is advised as a rule to fetch (one `config` op `rules` read per session, made only when advice would name a pointer). The attribution hook is removed. With a located config and no REST API
URL, `phase-guard` and `skill-enforcement` emit one `systemMessage` per session saying so (gate state and schema
facts come from the server) and then stay silent; `phase-guard-record` is always silent.

Seat skills take three hooks plus `skill-enforcement`. `seat-skill-hint` (PostToolUse `advance` and `items_read`, beside
`phase-guard-record`) reads a seat's first ok own-item read (an item-mode `context` read, or an ok `advance` element with
`newRole`), takes the seat from `callerSeat` (else a known seat `agent_type`), reads the item's `items_read` `schema` once
(`seats`, `notes`, `features`) and adds `SEAT SKILLS:` context naming the skills and their binding source, then a `SEAT RULES:` line naming
the seat's rule keys in order from the seat rule table (`lib/seat-rules.json`, resolver `lib/seat-rules.mjs`): the seat's protocol key (from
its served `enters` and `writes` when the server advertises `seatWrites`, else from its role), the keys the plugin adds for a writing seat, then
the seat's own rules (filtered by one served-rules read for the located `project.rootId`; unfiltered,
with a skip clause, when that read does not answer). The rules line is a hint only: nothing is recorded or refused for a rule. In a subagent it writes the agent's required
record, in the main session it hints once per item and role on an ok `advance` without a `seatToken`. `skill-record`
(PostToolUse `Skill`) records each skill a subagent loads. `seat-skill-gate` (PreToolUse `Edit|Write|NotebookEdit` and
`notes_write`) denies every gated call of a subagent (`SEAT SKILLS REQUIRED:`) until the record's skills are loaded or
preloaded by the agent file's `skills:`; a work seat is gated at file edits, a queue or review seat at its upserts of
its phase role. `skill-enforcement` does the same per note key in a subagent (`NOTE SKILL REQUIRED:`; a served rule is never
required). There is no release: an uninstalled skill answers `Unknown skill` and fires no hook, so the hint and every
denial name the binding source and tell the agent to stop and report the seat, the skill and the source instead of
retrying. A server without the `seatSkills` feature, a failed or schema-free item schema view, no REST URL, the main
session, an unknown seat, an empty list or an unwritable marker root (the probe cannot be written) is never refused.

The REST base URL resolves in this order: `TASK_ORCHESTRATOR_API_URL`, a project-level `client.json` (loopback only), the origin of the orchestrator's http(s) MCP registration (local `~/.claude.json` project entry, then `.mcp.json` - loopback only - then user `~/.claude.json`; `lib/mcp-registrations.mjs`), then the user-level `client.json`. `session-start` adds one warning line when the env var or a `client.json` points at a different origin than the registration.

## Mode gating

Plugin keys live under `extensions.claude-code` in `.taskorchestrator/config.yaml` (for example
`extensions.claude-code.steering`; the old `extensions.claude-code.orchestration.mode` is still read as a deprecated alias
when `steering` is absent or invalid, and `orchestration-context.mjs` prints one deprecation line per session while it is present).
Top-level 3.x keys such as `orchestration:` are ignored; a 4.0 server
rejects them on push, and `session-start` prints a `## Config Shape` line when it finds one.

`execution-mode.suppressionReason(hookInput, env)` is the shared gate for the four injecting context hooks. It returns
`headless` (`TASK_ORCHESTRATOR_MODE=headless-iteration`), then `subagent` (a non-empty `agent_id`), then `director` (a
file exists at `directorMarkerPath(session_id)`, written by `director-guard.mjs` when the director skill is invoked), or `null`.

## Retrospective trigger

Moved from the `session-retrospective` skill, which now only reads its arguments and runs the analysis. Step numbers below name that skill's steps.

This section is the `run` boundary, which `extensions.claude-code.retrospective.boundary: run` selects; the default boundary `scope` is described under [Retrospective firing](#retrospective-firing). At the `run` boundary a retrospective is owed per **closed** run that is not marked `retro`, and only to the session that opened or closed it through `runs_write` (its main thread or one of its subagents, which carry its session id). Any other session, a director included, stays silent about that run and leaves it unmarked; an orchestrator running in a session of its own handles its own run. Two hooks watch for it:

- `retro-trigger` (PostToolUse on `runs_write`) records every successful `op: open` and `op: close` in the session's state, and evaluates only on a successful `op: close`.
- `retro-backstop` (Stop) re-checks at the end of every turn, so a run this session opened that closed elsewhere (a subagent, a tool the trigger never saw) is still found. Only runs this session opened or closed count: another session's run is left unmarked for the session that drove it. A closed run is a confirmed boundary, so the backstop may dispatch as well as nudge.

Both ask REST `runs_read` `list` with `unmarked: retro` and `endedSince = now - 24h`, and read each run's terminal count from `runs_read` `frontier` (`data.counts.terminal`), for at most 5 runs per pass. In mode `dispatch` with a terminal count at or above `minItems` (default 3; `dispatchThreshold` is the older name, read when `minItems` is absent) they call `runs_write` `mark {runId, key: retro}` (REST only; first write wins, which is the cross-session dedupe; `marked: false` means another session won, so they stay silent) and emit the dispatch directive. A fix-cycle run (label `<runId>-a<n>`, the run a post-run fix cycle opens after the base run closed) always owes a retrospective in mode `dispatch`, whatever its terminal count: it often has one item, and the threshold would skip the only retrospective that sees the failure loop. Its directive names the base run, and that retrospective reports the base run's whole loop (Step 2, Fix-cycle cost). Below the threshold, in `nudge` mode (the default), or when the mark fails, they nudge once per run per session and never mark. There is no cross-session marker file (the server mark is the dedupe); per-session state (recorded opens and closes, runs already nudged) lives in `os.tmpdir()/task-orchestrator/<session>/retro.json`. A run whose frontier read fails is skipped that pass, and a close made by a subagent is recorded for the main session's backstop, not acted on. Without an API URL or a project rootId the backstop only nudges once per session, from the closes the trigger recorded.

`retro-ack.mjs` is the manual acknowledgement: `node retro-ack.mjs --run <id> [--run <id>]...` sends the same `runs_write` `mark {runId, key: retro}` over REST for each run (Step 8b calls it). It prints one line per id (`marked <id>`, `already marked <id>`, `mark failed <id>: <code>`, or `not marked <id>: no REST API configured`) and always exits 0.

**Director sessions.** A director never runs a retrospective in its own context, so for it both hooks always dispatch (mode `dispatch`, and at the `run` boundary threshold 0, whatever the config says; `off` stays off): every closed unmarked run it opened or closed (its in-session orchestrators' runs included) is marked first and then dispatched, so a later session does not dispatch it again. Without REST, `director-watch` dispatches once per run per session, only for a run this session opened or closed and closed within the last 24 h. The dispatch is ONE background agent that invokes this skill with a repeated `--run`.

**Label and session folder.** The dispatched agent is labelled `retrospective:<run8>` (`<run8>` is the first 8 characters of the first run id; `retrospective:unknown` with no run id) and its invocation gains `--session-dir "<dir>"` when the hook saw a transcript path ending in `.jsonl` (the folder is that path without the extension, backslashes turned into `/`). The label rule is in the run-wave `references/post-run.md`.

The settings (`mode`: `nudge` | `dispatch` | `off`; `minItems`, an integer of 0 or more; `boundary`: `scope` | `run`, default `scope`, an invalid value reads as `scope`) are read ONLY from `extensions.claude-code.retrospective`; a top-level `retrospective:` block is ignored and `cooldownMinutes` is gone. Headless iterations, `to_mod_retro` and `mode: off` make both hooks inert.

**Honest limit.** The mark is REST-only. Without a resolvable REST API URL (Step 8b prints `not marked ...: no REST API configured`), a manually run retrospective leaves its run unmarked, so it can nudge or dispatch again in a later session inside the 24 h window; Step 5b's `run:<runId>` search keeps that repeat from creating a second retrospective item.

## Retrospective firing

The setting `extensions.claude-code.retrospective.boundary` picks what a retrospective covers. `scope` (the default) owes one retrospective per **completed scope** (the item a run is scoped to, usually a feature), covering every run of that scope, fix-cycle runs included. `run` keeps the per-run rule of the section above. The rest of this section is the `scope` boundary; it needs REST and a project rootId (without them the hooks behave as in the section above).

**Keys.** Run marks only (`runs_write` `mark`: a key maps to the instant it was set; first write wins; a replay answers `marked: false`). They are written on every run of a group and read from the group's **anchor** run (earliest `openedAt`, ties by `runId`); a claim is won only when the write on the anchor answered `marked: true`.

| Key | Meaning |
|-----|---------|
| `retro-claim` | A session won the first dispatch for the group |
| `retro-retry` | The second dispatch was won (the first failed or its session died) |
| `retro-failed` | The second dispatch failed too; nothing dispatches again |
| `retro-skipped` | The triage found the group low-signal; always set together with `retro` |
| `retro` | Done: set by `retro-ack` at the skill's Step 8b, or by the hook together with `retro-skipped` |

**Grouping.** A pass reads the root's closed runs unmarked `retro` (closed in the last 30 days) and its open and paused runs. A run's group is its `scopeId`; a `scopeId` equal to the root counts as no scope; a fix-cycle run (label `<label>-a<n>`) without a `scopeId` joins the run labelled `<label>`, and joins no group (no mark, no directive) when that run is not in the pass; any other run is its own group. A group whose anchor carries `retro-failed` is ignored. A pass walks the groups (claims to retry first, then the newest) in waves of 5 and handles at most 5 actionable ones: a group that is not due, that this session may not act on yet (Ownership) or whose read failed takes no slot. No new wave starts 2000 ms after the pass began and no REST call starts 3500 ms after it, so the 5 s hook timeout holds; a group left over waits for the next pass. A REST read error, a truncated page or a missing scope item skips the group (or the pass) and writes nothing.

**Due.** A group with an open or paused run is never due. A scoped group is due when its scope item is terminal and the scope's subtree has nothing in `work` or `review`. A scope that is not terminal, with no open or paused run and its newest run closed more than 7 days ago, is **abandoned**: due, and its directive says the retrospective title starts with `[stale]`. An unscoped group is due when its run closed.

**Ownership.** A group is owned by the session whose `retro.json` `opened` or `closes` holds one of its runs (every successful `open` and `close`, in the main session or a subagent, is recorded; `ownsRun` in `retro-lib.mjs`). Owning one run is enough: a session that only opened a run owns its group. In mode `nudge` only an owned group acts, an abandoned scope included: when its owner is gone no nudge fires (a bystander is never nudged; `review-retrospectives` finds the scope). In mode `dispatch` an owned group acts at once. An unowned group (a bystander's) acts only when the project's configured mode is `dispatch` (a director's forced dispatch does not count), it is due and not abandoned, and it became due at or after the session started: a completed one 60 minutes after its scope turned terminal (an unscoped group: after its close), so a scope delivered in a later session is not lost, but a fresh session never inherits a group that was due before it began. The session start is the first parseable `timestamp` within the first 64 KB of the hook input's `transcript_path` (`sessionStartMs` in `retro-lib.mjs`); an unreadable transcript or no timestamp means no unowned group acts. An abandoned scope is its owner's alone. A dead claim is retried or given up by a bystander under the same due-after-start test (without the 60 minute hold); an owner's claim is unchanged.

**Triage (both modes, zero model tokens).** For a group that can act and has no claim yet (due and owned, or a bystander's in a dispatch-configured project that became due after the session started) the hook reads the group's items over REST (the scope's subtree minus the scope; for an unscoped group the items of the run's ended seats, at most 20) and drops the types `retrospective-trend`, `container`, `improvement-proposal` and `agent-observation`. The group is **low-signal** unless one of these holds, checked in this order: a fix-cycle run in the group; terminal items at or above `minItems`; an `agent-observation` created since the group's first run opened whose title or summary names one of the group's runs, its scope or one of its items (a full page of 200 with more rows is a signal too); an item whose `session-tracking` note is missing or whose `Outcome:` does not start with `success` or `implemented`, or whose `Friction:` or `Deviations:` is not `none` (trimmed, any case, one trailing period). A low-signal group gets `retro-skipped` then `retro` on every run and the hook says nothing.

**Dispatch.** A due, not low-signal group that this session owns (or, in a dispatch-configured project, a bystander's that became due after the session started) with no `retro-claim` is claimed and dispatched. Groups won in one pass share ONE directive that repeats `--run`. A session makes at most one first claim an hour (`lastDispatchAt` in `retro.json`); retries do not count. The directive no longer says to skip when the feature has active items (the scope is complete when it fires); it still tells the session to hold it until background work has finished.

**Retry and give-up.** A group whose anchor has `retro-claim` and no `retro` is retried (`retro-retry`) when it is this session's claim and that claim is marked failed, or when this session holds no such claim and the claim is more than 20 minutes old (a dead session's claim: another session may take it over, if the group became due after that session started). A group with `retro-retry` and no `retro` gets `retro-failed` on the same two tests; the session that won it nudges once (never a director) and nothing fires again. Only a session in mode `dispatch` retries.

**Failure detection (`retro-subagent-stop.mjs`, SubagentStop).** With claims in `retro.json`, a stopping subagent triggers a `runs_read` `get` of each claim's anchor (all of them in parallel): `retro` present drops the claim; absent, and the first 256 KB of `agent_transcript_path` hold `/session-retrospective` and the anchor run id, marks the claim `failed: true`. The next Stop pass then retries without waiting 20 minutes. The hook only edits the session state and always answers `{}`; a background agent's SubagentStop is assumed to carry `agent_transcript_path`. When this session's own SubagentStop lacks it, the claim stays unfailed here and this session never takes it over; a later session takes the claim over after 20 minutes.

**Nudge mode.** A due, owned, not low-signal group (a completed or abandoned scope this session owns) is named in ONE nudge, once per session; an unowned group is never nudged. A nudge carries one `/session-retrospective --run a --run b` invocation and `--session-dir "<folder>"`.

**Director sessions.** A director is always in mode `dispatch` and `minItems` is not zeroed (it is the triage's size signal); it never gets a nudge. Without REST `director-watch` keeps its per-run dispatch, because grouping needs REST.

**Per-session state.** `os.tmpdir()/task-orchestrator/<session>/retro.json`: `opened`, `closes`, `sawClose`, `nudged`, `backstopNudged`, `claims` (`{anchor, runs, key, at, failed}`), `lastDispatchAt` (ISO instants).

**Debugging.** `RETRO_HOOK_DEBUG=1` persists the trigger's input to `os.tmpdir()/task-orchestrator/debug-last-invocation.json` so a live firing records the real payload shape.
