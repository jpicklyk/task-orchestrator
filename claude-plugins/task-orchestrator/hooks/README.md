# Plugin hooks

Hook entrypoints live in this directory and are wired by `hooks-config.json`. Shared plumbing lives in `lib/`;
every module is pure at import (no top-level I/O) and never throws.

| Module | Role |
|--------|------|
| `lib/stdin.mjs` | `readHookInput()` / `parseHookInput(text)`: hook stdin as a plain object, or `null` when unreadable. |
| `lib/emit.mjs` | Output builders (`contextOutput`, `denyOutput`, `blockOutput`, `systemMessageOutput`) and the matching one-write stdout writers (`emit`, `emitEmpty`, `emitContext`, `emitDeny`, `emitBlock`, `emitSystemMessage`). |
| `lib/markers.mjs` | Temp-dir marker files: `sessionMarkerPath` (per session), `sharedMarkerPath` (cross-session), `readMarker`, atomic `writeMarker`, `createMarkerOnce`. |
| `lib/envelope.mjs` | `parseToolResult` reads the 4.0 result envelope (`kind` and `retryAfterMs` as the server sends them), from `structuredContent` or, without it, from the text: a whole JSON text, or the error envelope on the last line of an MCP error text (`parseEnvelopeText`); `isLegacyShape` flags a 3.x payload. |
| `lib/ops.mjs` | `opsOf`, `selectOf`, `opItemIds`, `resultItemIds`: helpers over the `ops` array of a tool input and its result. |
| `lib/served-rules.mjs` | `loadServedRuleKeys(sessionId, rootId)` (one `config` op `rules` list read per session, cached in the `served-rules` session marker, null on any failure) and `splitPointers(names, keys)` (`{rules, skills}`): a pointer that is a served rule key is fetched, any other is invoked as a skill. |
| `lib/seat-skills.mjs` | `seatSkillsFor(declared, seat, opts)`, `seatNameFor`, `resolveSeatSkills` and `loadSeatSkillDefaults`: a seat's declared `skills` list (`[]` = none) when the server lists the `seatSkills` feature, else the defaults table `lib/seat-skill-defaults.json` (which maps each seat to its default skills), else none. Pure at import; the JSON is read on first call. Null options act as `{}`. |
| `lib/seat-skill-state.mjs` | Per-(session, agent) seat-skill state, never phase-guard-record's file: the required record `seat-skills-<agent>` (`readRequired`, `writeRequired`), one `skill-loaded-<hash>-<agent>` file per loaded skill (`recordSkillLoaded`, `isSkillLoaded`, `missingSkills`; race-free under parallel Skill calls), the writability probe `seat-skill-armed-<agent>` (`armDenial`, written before each denial; a failed write allows the call), `bindingSourceLabel` (`declared` -> `schema`, `default` -> `plugin default`), `preloadedSkills(agentType)` (the agent file's frontmatter `skills:`), `UNKNOWN_SKILL_TEXT` and the frozen text prefixes. |
| `lib/api-client.mjs` | URL and token discovery, `fetchWithTimeout`, `callOp(tool, body)` over `POST /api/v1/ops/{tool}`, and `wellKnown()`. |
| `lib/server-compat.mjs` | `assessServer` / `checkServer` (major 4 with the `seats` feature) and `legacyShapeWarningOnce`. |
| `lib/tool-names.mjs` | Generated by `scripts/gen-call-shapes.mjs`: `TOOLS`, `PROFILES`, `WRITE_TOOLS` and `ERROR_KINDS`. |

## Hooks on the envelope

The write-path hooks read the 4.0 contract, not the 3.x one. `phase-guard-record` (PostToolUse `advance` and `items_read`) and
`dispatch-hint` parse `tool_response` with `parseToolResult` and read every `results[i]`: an element is recordable when
`ok` with a `newRole` (`gate_blocked` records nothing: it means a note is missing). A phase-owner seat (`implementer` or
`reviewer`) already in its phase sends no `start`, so its first item-mode context read is recorded instead, when the
item's role is the one the seat owns and nothing is recorded yet; a non-empty top-level `seatToken` marks a run seat,
which is never recorded. A 3.x-shaped result records and hints
nothing and shows the legacy-shape warning once per session. `phase-guard` (SubagentStop) reads each recorded item's
gate with `items_read` `select: "context"` (`POST /api/v1/ops/items_read`) and skips `workflow-subagent`. It blocks a stopping seat only on that seat's own missing notes: when the gate carries `missingBySeat` and the view's `seats` names the stopping seat, only `missingBySeat[seat]` counts (the `unowned` bucket and other seats' keys never block); otherwise it falls back to the flat `missing` list minus the test-author-owned keys (kept when the stopping seat is the test author). When a block hint would name the gate's `skillPointer`, it reads the root's served rule keys once (`config` op `rules`, shared session marker, read capability) and hints a pointer that is a served rule key as a rule to fetch.
`skill-enforcement` (PreToolUse `notes_write`) acts on `ops[]` elements with `op: "upsert"` and takes skill and
`maxLength` facts from the server: one `config` `effective` read per session, cached in a session marker, and the
item's `items_read` `schema` view per op. A note skill that is a served rule key is advised as a rule to fetch (one `config` op `rules` read per session, made only when advice would name a pointer). The attribution hook is removed. With a located config and no REST API
URL, `phase-guard` and `skill-enforcement` emit one `systemMessage` per session saying so (gate state and schema
facts come from the server) and then stay silent; `phase-guard-record` is always silent.

Seat skills take three hooks plus `skill-enforcement`. `seat-skill-hint` (PostToolUse `advance` and `items_read`, beside
`phase-guard-record`) reads a seat's first ok own-item read (an item-mode `context` read, or an ok `advance` element with
`newRole`), takes the seat from `callerSeat` (else a known seat `agent_type`), reads the item's `items_read` `schema` once
(`seats`, `notes`, `features`) and adds `SEAT SKILLS:` context naming the skills and their binding source, then a `SEAT RULES:` line naming
the seat's rule keys in order from the seat rule table (`lib/seat-rules.json`, resolver `lib/seat-rules.mjs`): the role's protocol key, the
keys the plugin adds for the role, then the seat's own rules (filtered by one served-rules read for the located `project.rootId`; unfiltered,
with a skip clause, when that read does not answer). The rules line is a hint only: nothing is recorded or refused for a rule. In a subagent it writes the agent's required
record, in the main session it hints once per item and role on an ok `advance` without a `seatToken`. `skill-record`
(PostToolUse `Skill`) records each skill a subagent loads. `seat-skill-gate` (PreToolUse `Edit|Write|NotebookEdit` and
`notes_write`) denies every gated call of a subagent (`SEAT SKILLS REQUIRED:`) until the record's skills are loaded or
preloaded by the agent file's `skills:`; a work seat is gated at file edits, a queue or review seat at its upserts of
its phase role. `skill-enforcement` does the same per note key in a subagent (`NOTE SKILL REQUIRED:`; a served rule is never
required). There is no release: an uninstalled skill answers `Unknown skill` and fires no hook, so the hint and every
denial name the binding source and tell the agent to stop and report the seat, the skill and the source instead of
retrying. A server without the `seatSkills` feature, a failed or schema-free item schema view, no REST URL, the main
session, an unknown seat, an empty list or an unwritable marker root (the probe cannot be written) is never refused.

The REST base URL resolves in this order: `TASK_ORCHESTRATOR_API_URL`, a project-level `client.json` (loopback only), the origin of the orchestrator's http(s) MCP registration (local `~/.claude.json` project entry, then `.mcp.json` - loopback only - then user `~/.claude.json`; `lib/mcp-registrations.mjs`), then the user-level `client.json`. `session-start` adds one warning line when the env var or a `client.json` points at a different origin than the registration.

## Mode gating

Plugin keys live under `extensions.claude-code` in `.taskorchestrator/config.yaml` (for example
`extensions.claude-code.orchestration.mode`). Top-level 3.x keys such as `orchestration:` are ignored; a 4.0 server
rejects them on push, and `session-start` prints a `## Config Shape` line when it finds one.

`execution-mode.suppressionReason(hookInput, env)` is the shared gate for the four injecting context hooks. It returns
`headless` (`TASK_ORCHESTRATOR_MODE=headless-iteration`), then `subagent` (a non-empty `agent_id`), then `director` (a
file exists at `directorMarkerPath(session_id)`, written by `director-guard.mjs` when the director skill is invoked), or `null`.

The table lists one row per script registered in `hooks-config.json` and what it does at this version. "Not gated" means
the hook has no check for that column; "non-injecting" means it adds no context. `plan-capture.mjs` is not gated and injects only in a project session: there (a located project config with a `rootId`) it adds one line, `plan stashed as plan document ...` or `plan not stashed (<why>)`, and in any other session nothing; it never blocks plan approval.
