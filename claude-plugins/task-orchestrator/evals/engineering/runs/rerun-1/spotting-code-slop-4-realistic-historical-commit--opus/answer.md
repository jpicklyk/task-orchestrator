I've written the review to `review.md` with four findings and a verdict of **changes**. The two affected test files (`retro-observation-scope` and `retro-session-coverage`) pass, 131 of 131. I also checked that the server accepts the hook's new list request (`sort`, `order`, `fields: ["summary"]`).

1. **The hook ignores where an observation sits** (`retro-lib.mjs:579`). It decides an observation is linked only by looking for an id or label in its title or summary. An observation filed under the scope or under one of its items is the clearest possible link. The hook already reads it in the subtree, then filters it out. Unless its text also repeats an id, the group is skipped as low-signal and nobody is told. Before this commit, such an observation always counted.
2. **Label matching catches common words** (`retro-lib.mjs:324`). Any run label of 8 or more characters counts as a match when it appears as a whole word, in any case. Labels are free text, so a label like `refactor` or `database` would match unrelated observations. That brings back the bug this commit fixes for those groups.
3. **The skill doesn't read observations the way the hook does** (`SKILL.md:39`), even though the CHANGELOG says it does.
   - It sets no sort order, so it gets the newest 200 observations; the hook reads the oldest 200.
   - It says nothing about following the next page when there are more than 200, so it silently drops observations past the first page. The hook treats that same case as a reason to run the retrospective.
   - It leaves out the hook's rule that an id must not be glued to other letters or digits, so the two can disagree about the same row.
4. **Unrelated wording changes in the skill** (`SKILL.md:136`, and line 60). The commit rewords most of the skill, and some edits lose meaning. "one call" was dropped from the run-marking step, which told the agent to run `retro-ack.mjs` once with every `--run`. "Lists and matching" became "Matching", which drops the pointer to where the trend list calls are defined.
