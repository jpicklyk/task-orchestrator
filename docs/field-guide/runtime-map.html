Where it runs and who talks to it

One Docker image, one SQLite file. It runs as a throwaway container per session or as a persistent local server shared by every project, and one tool dispatcher answers the MCP tools and the REST tool route, so the same gate logic and the same response envelope serve both.

Inside the server

Two ways to run it

Tool profiles

Over HTTP the server mounts /mcp (orchestration), /mcp/knowledge (a smaller read and write set) and /mcp/director (read tools, run control and decisions, no read that returns a note or document body). Over stdio one profile is served, picked by MCP_TOOL_PROFILE. Any other value fails startup.

Auth follows the REST setting

With API_ENABLED=true and API_AUTH_MODE=bearer or jwks, every /mcp* path requires the credential. HTTP with API_ENABLED=false needs MCP_ALLOW_UNAUTHENTICATED=true or startup fails. A director credential reaches only the director path.

Startup is gated

Flyway is the only schema path (SCHEMA_MODE is migrate or validate), under a <db>.migrate.lock file lock, then data steps such as server-config-import run. The readiness marker at READINESS_FILE is written only after all of that and the transport bind. Depth is in fleet-deployment.md.

The REST API, for everything that is not an agent

Dashboards, CI jobs and the plugin's own hooks use HTTP under /api/v1, switched on with API_ENABLED=true. Every tool is reachable as POST /api/v1/ops/{tool}, so an advance over REST is the same call, with the same gate logic, as over MCP.

Writes are guarded

A write may pass expectedVersion, so a stale client gets a 409 version_conflict and cannot overwrite. Each element of ops[] may carry an idempotencyKey, kept for 24 hours per principal, tool and key, so a retry replays its first result. An Idempotency-Key header is a 400 invalid_request.

Errors say what to do

Every tool answer is { ok, data | error, meta: { reqId } }, and an error is { code, kind, message, detail?, fix? }. A failed gate is 409 gate_blocked with the missing notes. A failed element of a non-atomic batch answers 207 partial_failure, with its own code in its data.results[i] element. The reqId also keys the call log and the server log lines for that call.

Where REST differs from MCP

The caller is always the credential's principal, on REST and on /mcp alike, and an actor in the body is refused as unknown_parameter. A REST advance is bound by claim ownership and by leases, as on MCP. Lease administration and the event stream exist only here. report (usage, gates, contention, waste and rollup aggregates over server telemetry) is served at POST /ops/report and, over MCP, only on the director profile.

What the Claude Code plugin adds

The server works with any MCP client. The plugin wires it into a Claude Code session through hooks, in the order a feature normally unfolds.

  1. SessionStartInjects workflow conventions and project scope. Syncs the project config to the server.
  2. EnterPlanModeReads existing items and schema gates first, so the plan covers what the gates will ask for.
  3. ExitPlanModeTurns the approved plan into items, dependency edges and queue notes before any code is written.
  4. SubagentStartHands an implementer or reviewer its protocol: enter your phase, fill its notes, return.
  5. advanceRecords which phase a sub-agent entered, and hints the dispatch profile (agent, model, effort) for the next one.
  6. SubagentStopSends a sub-agent back if the phase it entered still has required notes missing.

Claims in practice

Four answers to a claim

claimed: true; a claim_held error (pick another item); a select with no match (claimed: false, no reason: stop or wait); and a select with a reason (claim_held or dependency_unmet: matches exist but none can be claimed now, retry after retryAfterMs). A claim belongs to one principal and assignment, and taking a new claim releases the caller's other claims (one at a time). Each element may carry an idempotencyKey.

Claims clean up after themselves

Any transition into terminal clears the claim, and a reopened item starts unclaimed. A crashed agent's claim simply expires. Nothing has to clear it: a background sweep only records the expiry event.

Who holds it stays private

Lists and searches show only whether an item is claimed. The holder's identity appears in one place: the claimDetail of items_read context for that item.

Local is one principal

Every stdio or local-mode session is the same local caller, so they share claims and note ownership and never contend. Telling agents apart takes a credential or a run seat token for each.

Sessions stick to a caller

An MCP session is bound to the principal that opened it, and another principal on that session gets a 401. A director credential reaches only the director endpoint. A wrong token is the JSON error envelope, not a JSON-RPC error.

Old identity settings stop startup

No request carries an actor or a proof any more. A leftover actor_authentication: or auditing: block in the server config, or a set DEGRADED_MODE_POLICY variable, fails startup rather than being ignored.

JWKS stays fail-closed

API_JWKS_MAX_STALE_SECONDS is how old a cached key set may be and still be served after a failed refresh (default the larger of an hour and the cache TTL). Past it, requests get 503 unavailable. API_JWKS_URL must be https and resolve only to public addresses, so a private or Docker-network host is refused. Loopback over plain http is allowed only with API_JWKS_ALLOW_INSECURE_URL=true.

Reports read telemetry

The report tool aggregates the server's own call log and events into usage, gates, contention, waste and rollup views, for a director or a dashboard.

Old data ages out

A pruner trims tables on a schedule: RETENTION_EVENTS_DAYS (180), RETENTION_AUDIT_EVENTS_DAYS (0), RETENTION_LEASE_HISTORY_DAYS (365) and RETENTION_CALL_LOG_DAYS (90). A value of 0 keeps that data forever. Details are in fleet-deployment.md.

Three independent switches

Orchestration

Always on. Transitions, gates, dependencies and cascades work with no further setup.

Claims

Opt-in. Agents take time-limited ownership of an item with the claim op of advance. The server then fences the item to its holder: a transition, note write, item update or dependency write by anyone else is not_claim_holder.

Credentials

Opt-in and separate from claims. With a bearer or JWKS mode, REST and every /mcp* path require a credential, so attribution is proven and no longer shared. Without one, HTTP with the REST API off must opt in with MCP_ALLOW_UNAUTHENTICATED=true.
