One call moves an item. The gate decides.

Every work item with a lifecycle sits in one of five roles. (A schema with lifecycle: none gives its items no role and no transitions.) Agents never edit status directly. They call advance with a trigger, and that call is where the server checks claims, dependencies and required notes.

The gates run in a fixed order and the first to fail answers: claim ownership, seat, the table above, dependencies, notes, leases. Entering terminal also clears the item's claim. To see which gate would answer without sending anything, read items_read select="context": gateStatus.canAdvance and, when false, gateStatus.blockedBy (table, dependency, note or lease).

A block carries a reason

block and hold take a reason: awaiting_decision (with the decisionId of an open decision), dependency, resource or manual (the default). Reads report it, and an awaiting_decision block reports resumable once its decision is no longer pending. Answering a decision never resumes the item: someone still sends resume.

Roles are fixed, labels are yours

The role is what the server reasons about. Alongside it, each transition sets or clears a status label: display text for people and dashboards. The five roles never change. The labels can be renamed per project.

An explicit label wins. With none configured, entering blocked keeps the label the item has and any other transition clears it. The label comes back on every transition result and on item queries. Filter and gate on the role. Show the label.

When a call fails

Every failure carries a kind that says whether retrying can help, and a code to branch on. An agent never has to parse the message text.

{
  "ok": false,
  "error": {
    "code": "claim_held",
    "kind": "transient",
    "message": "...",
    "detail": { "itemId": "550e8400-...", "expiresAt": "2026-10-16T13:15:00Z", "retryAfterMs": 420000 },
    "fix": "...",
    "retryAfterMs": 420000
  },
  "meta": { "reqId": "..." }
}

A one-element write without atomic that fails answers partial_failure, with this error object at data.results[0].error.

An idempotencyKey makes a write safe to resend

Each element of a write call may carry an idempotencyKey. The server records a committed element for 24 hours per principal and tool and returns its stored result again (replayed: true) instead of running it twice. The same key with a different element is idempotency_mismatch.

Same key on every retry

No response arrived, such as a timeout: resend with the same key. Only an element that committed is recorded, so an element that failed runs again when you retry with the same key.
