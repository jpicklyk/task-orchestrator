A process that proposes its own fixes

Friction noticed during work becomes a tracked item. Friction that recurs becomes a trend. A trend seen twice becomes a concrete proposal to change the config, and a person decides whether to adopt it.

The loop

What starts a retrospective

A retrospective is owed for each closed run that is not yet marked retro. The retro-trigger hook watches runs_write and acts only on a successful close. At the end of every turn retro-backstop checks again, so a run closed by another session is found too, when the hook can reach REST with a project rootId. That pass looks back 24 hours and checks at most 5 runs. What happens next is set by extensions.claude-code.retrospective.mode in the project config.

nudge, the default

The session is told a retrospective is suggested and given the command to run. The user decides.

dispatch

When at least dispatchThreshold of the run's items (default 3) reached terminal, the hook tries to mark the run, and the session that wins the mark is told to launch one background retrospective agent. A session that loses the race stays silent. Smaller runs still get a nudge, and so does a run whose mark failed. A director session is treated as dispatch unless the mode is off.

off

Nothing is emitted. Retrospectives run only when someone invokes /task-orchestrator:session-retrospective.

The dedupe is server-side: runs_write mark with key retro, first write wins, so two sessions never both dispatch. The mark is REST only. There is no cooldown. Without REST or a project rootId the hook only records the close, and the end-of-turn backstop nudges once. Work done outside a run has no trigger, so run the skill by hand. The settings are read only from extensions.claude-code.retrospective; a top-level retrospective: block is not read.

By hand, --run <runId> scopes the analysis to one run. --deep hands the trend matching to the retro-analysis workflow, in the main session only; the skill still performs every write.

What the retrospective reads and scores

It reads the session-tracking note on each item of the run (up to 20), plus the optional delegation-metadata note recording which model did the work. Then it scores five things.

  • Schema effectiveness

    Do the required notes exist at a sensible size? Under about 50 tokens is flagged as sparse.

  • Delegation alignment

    Did each task run on the model the delegation table expects?

  • Note effectiveness

    Did the specs hold up? Work notes that say "deviated" or "assumption was wrong" flag a spec gap.

  • Plan-to-execution alignment

    What share of planned items finished, and how many were added mid-run?

  • Friction synthesis

    Tool errors, excess round-trips, workarounds and confusing calls.

The result is a retrospective item under the Session Retrospectives container, with queue notes session-metrics, workflow-evaluation and improvement-signals, and a work note actions-taken written last.

A trend is a counter with evidence

title:   trend: thin-review-checklist — review notes
         restate the plan instead of checking it
summary: Reviewers copy acceptance criteria without
         evidence. Sessions: 2. Last seen: 2026-09-30.
type:    retrospective-trend
tags:    ["retrospective-trend", "note-quality"]

notes:   evidence-2026-09-24-4c1e   (work)
         evidence-2026-09-30-b07a   (work)

Matched by key

The short key in the title is the trend's identity. A new finding is matched to an existing key first, then by search when the match is uncertain.

Recurrence adds evidence

Each session that sees the finding again adds one evidence note and increments the count. The summary is rewritten to stay short.

Two sessions make a proposal

A trend at Sessions: 2 or more graduates. Trend items are never started or completed. They are cancelled when archived. Evidence notes are added as needed, not required by the schema.

The example values are illustrative. The format is the skill's own.

Deciding a proposal

A proposal is a work item with three required notes, one per phase: proposal, adoption-decision and outcome-verification. Pick a scope and a decision to see where it ends up.

A project proposal changes one project's schemas or workflow. A global proposal changes the shared server config or the plugin itself.

    Observations: the raw material

    An observation is a small item recording something the tooling got wrong or made hard. Each is its own root, low priority, tagged agent-observation plus one kind.

    optimizationfrictionbugmissing-capability

    Before one is created, the backlog is searched for the same issue, so repeats add context to an existing item. They stay outside every project because tool friction is not specific to one codebase.
