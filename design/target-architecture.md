# Target architecture

The one picture every change to Task Orchestrator is judged against: the zones that say what kind of statement something is and who owns it, the host channels that carry text to an agent, the actors that act through those channels, and a responsibility matrix with one row per system concept. It is for contributors and reviewers who need to decide where a statement, check or default belongs, and for whoever plans the work packages in [architecture-breakdown.md](architecture-breakdown.md) that move today's leaks. It describes the state of 2026-11-26 (origin/main `ce75ca2a8`): each matrix row says what is true today and what the target is, and the target is not built yet unless a row says so. The seams named here are catalogued in [seams.md](seams.md); the context map is [system-context.md](system-context.md). The why behind settled choices is in [decisions/](decisions/README.md), notably [0016](decisions/0016-seat-capability-and-orchestrator-notes.md), [0017](decisions/0017-orchestrator-binding.md) and [0018](decisions/0018-content-placement.md). Terms follow [GLOSSARY.md](../GLOSSARY.md).

Companion documents: [seat-model.md](seat-model.md) (seats, protocol choice, orchestrator notes), [config-layering.md](config-layering.md) (server config, project config, traits, defaults tables), [run-execution.md](run-execution.md) (front door to retrospective), [enforcement-map.md](enforcement-map.md) (every check and where it sits) and [journey-overlay.md](journey-overlay.md) (the user journeys walked against this picture).

## 1. Zones

A zone is a kind of content with one owner. A file holds content of one zone only; a file that holds two is a finding. Zones are analysis words: the only zone-level terms meant for shipped text are "server config", "project config", "shipped default" and "host" (each a proposed glossary entry).

| Zone | Owner | Holds | Never holds |
|---|---|---|---|
| **Z1 Server** | Tool author | State and gates: items, notes, dependencies, documents, lifecycle and phase gates, seat facts and owning seats, runs, run tokens and seat tokens, decisions and their classes, credentials and profiles, config parsing, validation and serving, and the tool contract (`@Doc`, tool and op prose, MCP instructions). It says whether something exists, who owns it and whether a transition is allowed. It serves what config declares even where it does not act on it (`skill`, `rules`, `skills`; in the target also note `purpose`, seat `writes`, the orchestrator binding and each note's computed owner). | Engineering craft; a project's workflow decisions |
| **Z2 Plugin mechanics** | Tool author | The server's client-side half: mechanics skills, hooks (timing and enforcement), agent definitions (role-particular text and tool lists), workflows and scripts, the protocol rules, and host integration (Agent `model`/`effort`, ToolSearch, plan mode, `AskUserQuestion`). It explains how to use the tools to run work and decides only from facts the server serves or the host reports. | A project's notes, seats, commands or policy; a process step a project could choose differently |
| **Z3 Shipped defaults** | Tool author, replaceable by the project | Generic policy that reaches the platform through the same seam a project uses to replace it: engineering skills, conduct rules given as seat defaults, the defaults tables (seat rules and seat skills keyed by seat name, and the orchestrator row), `dispatch-policy.json` classes and tiers, the server config's process types and seat-less mechanism traits, setup templates, and the presentation reference. | A default that reaches the platform any other way (that is a misplacement, however generic it reads) |
| **Z4 Project process** | The project | The project's workflow decisions: its schemas (types, phases, notes and their guidance, seats and their `writes`, traits), the orchestrator binding at root and trait level, decision classes, `extensions.claude-code` (steering, retrospective, template record, approval routing), project rules, the process fields of the run profile, and its dispatch overlay. | Tool mechanics; another project's process |
| **Z5 Project toolchain** | The project | What the project's work runs on: build, tests, linters, CI, deploy, the toolchain fields of the run profile (`verify[]` commands, `shell`, paths), project skills (repo mechanics, and the skills a note's `skill:` or a seat's `skills:` points at), project commands, and the repo facts in the project instruction file. | Decisions the schema makes |
| **Z6 User stance** | The user | What the user chooses across projects: the output style (voice, presentation, analysis stance), the user-level instruction file, auto memory (user facts, host traps), and the user-level config of a personal root. It must survive the swap test and the owner test (section 5). | A project's process; a tool's mechanics |
| **Z7 Host** | Shared runtime (Claude Code) | Events, subagents, permission modes, plan mode, settings and permissions, the plugin cache. | Anything a project or the tool decides; knowing the host is allowed only in Z2's host-integration parts |

"Server config" (the global floor) is `deploy/global-config/.taskorchestrator/`, imported at boot and shared by every root; it is Z3 content delivered through a Z1 seam. "Dogfood config" is this repository's own `.taskorchestrator/`, which is Z4 content for this one project and must never be the place a shipped default is authored. [config-layering.md](config-layering.md) has the delivery paths.

## 2. Host channels

The second axis: how text reaches an agent, and when. A channel is not an owner; each may carry only the zones listed. "May carry" is the target.

| Channel | In context | Chosen by | Enforced | May carry | Must not carry |
|---|---|---|---|---|---|
| **C1 Instruction files** (project, nested and local `CLAUDE.md`; user `~/.claude/CLAUDE.md`) | Always | The level's owner | No | Z5 repo facts, traps, where things live, guard rules and their tests; Z6 at user level; pointers to records | Design records, process, method |
| **C2 Output style** | Always, for the session | User | No | Z6 stance, voice, a presentation override | Mechanics, project process, protocol |
| **C3 Skills** (mechanics, engineering, project) | On trigger or binding | Description, binding, user | No (hooks gate a bound skill) | Z2 mechanics, Z3 engineering method, Z5 repo mechanics | Every-turn facts; another zone's policy |
| **C4 Hooks, context** (SessionStart, SubagentStart, event hints, director compact) | At events | Plugin, steering | No | Z2 mechanics and live state; resolved binding lines (RULES, SKILLS) | Presentation, process policy, engineering content |
| **C5 Hooks, enforcement** (PreToolUse guards, Stop, SubagentStop) | At events | Plugin | Yes | Z2 checks on facts the hook can see | Judging prose; facts only the server holds |
| **C6 Agent definitions** | That subagent | Dispatcher | Tool list yes, prose no | Z2 role-particular conduct, tool lists | Protocol, workflow order, project note keys |
| **C7 Workflow prompts** (`workflows/*.js` in the plugin) | Inside a Workflow run | run-wave | No | Z2 text rendered from served facts and resolved keys | Literal note keys, commit style |
| **C8 MCP instructions, `describe`, `@Doc`** | On connect or describe | Server | Contract yes | Z1 tool contract | Project process |
| **C9 Served rules** (`config` `rules`, `docs` kind `rule`) | Fetched per dispatch | Rule table plus declared lists | No | Z2 protocol rules, Z3 seat defaults, Z4 project rules | Method, note shapes, procedures |
| **C10 Note guidance** (`items_read` `schema`) | When a note is filled | Schema owner | `maxLength` only | Z4, or Z3 through server config traits: what a note records and its shape | How to do the work (that goes to the bound skill) |
| **C11 Settings and permissions** | Applied by the host | User, project | Yes | Z7 hard limits, plugin enablement, style selection | Advice |
| **C12 Memory** (auto memory index and files) | Always (index) | User and agent | No | Z6 user facts, host traps | Rules restated; standing authorizations |

Slash commands are a user entry, not a channel for content: a project command is Z5, a user-invocable plugin skill is Z2.

## 3. Actors

Actors are a third axis, not zones: they act through channels on content that lives in zones. The session layers of [0001](decisions/0001-two-session-layers.md) apply unchanged.

| Actor | Does | Server identity | Conduct reaches it through | Reads |
|---|---|---|---|---|
| **User** | Decides: answers the decisions that reach it, accepts work, chooses its session mode and stance | A credential. Only a credential of kind `human` is exempt from seat enforcement (`isHumanCaller`, `platform/call/CallContext.kt:101`). Today stdio, unauthenticated HTTP and `API_AUTH_MODE=none` attach the local principal, of kind `agent` (`platform/call/LocalPrincipal.kt`), so the user's own session is not exempt on default transports | C2, C1 (user level), C12 | Everything |
| **Director** | Decides on the user's behalf within each decision class, escalates the rest, acts on the board, hands work to orchestrators; never drives | A call with no seat token. Today decision ops and run control are served on the director profile only and authority is tested by profile (`RunPermissions.isDirector`, `run/internal/app/RunPermissions.kt:45`). Target: decision authority from the class plus a credential's `decide` capability, on every profile that needs it ([0003](decisions/0003-role-neutral-decisions-surface.md)) | The director skill; `director-guard` enforces altitude ([0002](decisions/0002-director-on-orchestrator-tools.md), [0014](decisions/0014-director-reads-skills-runs-plugin-scripts.md)) | Ids, counts, state, short reasons, one decision request in full, run rollups |
| **Orchestrator** | Drives: plans, sizes, dispatches seats, advances, resumes an item after its decision is answered, raises decisions; never answers one. The user's session in orchestration mode, or a background agent running a run | Inside a run, the **run token** (proposed glossary entry): the credential `open` returns, wire `orchestratorToken` (deprecated alias `coordinatorToken`, stored value `coordinator`). It may send any trigger on any member and write **orchestrator notes** (proposed glossary entry). Outside a run it calls with no token | Today: prose in the SessionStart core hook, the background orchestrator brief and project skills. Target: the **orchestrator binding** (proposed glossary entry), the `orchestrator:` block at root and trait level, resolved into one RULES and SKILLS line ([0017](decisions/0017-orchestrator-binding.md)); `protocol.orchestrator` always first | Note bodies it needs to drive; hands the layer above only ids, counts and short reasons |
| **Seat agents** | Fill the notes their seat owns in one phase of one item; a writing seat also changes files and commits | A seat token from `assign`, for one run, item, seat and attempt | The dispatch: its protocol rule, seat rules and seat skills (C9, C3, C6, C4 SubagentStart). Target: the protocol rule is chosen from served `enters` and `writes`, and the dispatch lists the seat's effective `transitions` ([seat-model.md](seat-model.md)) | The item's notes, minus `reads_exclude` |

The word **orchestrator** names only the session layer. Three other concepts carry the word as a composition and none of them is a seat ([0016](decisions/0016-seat-capability-and-orchestrator-notes.md)):

| Concept | Name | Today | Target |
|---|---|---|---|
| The reserved owner of notes the orchestrator writes | Orchestrator note | A seat named `orchestrator` must be declared, with a phase that means nothing, for `seat: orchestrator` notes to be owned (`model/note/OwningSeat.kt:26`; the dogfood declares it at `.taskorchestrator/config.yaml:61`, `:86`) | `seat: orchestrator` on a note entry is valid in every schema; a seat named `orchestrator` or `coordinator` warns for one release, then is refused; the server serves each note's computed owner |
| The server's run identity | Run token | Stored as a run-scoped `run_seats` row and listed among `allowedSeats` in a seat refusal (`lifecycle/TransitionPolicy.kt:377`) | Described as a token, never a seat; refusal details stop listing it as a seat |
| Where the orchestrator's rules and skills attach | Orchestrator binding | Prose in three channels | The `orchestrator:` block at root and trait level; a schema reaches a trait's binding through `default_traits`; it never makes a type seat-aware |

## 5. How to judge a change

For each new or changed statement, rule, check or default:

1. **Place it.** Name its kind and the zone it belongs in, not the zone it sits in. Ask: if a quite different project adopted the tool tomorrow, would it want this different? No: mechanism (Z1, Z2). Yes, but most would accept a starting point: a shipped default (Z3), reachable only through the seam a project uses to replace it. Yes, with no sensible starting point: the project's (Z4, Z5).
2. **Find its seam.** Content placed in Z3 or Z4 must reach the platform through a seam in [seams.md](seams.md). No seam means a gap: add the seam, never a sterner rule.
3. **Hiding question.** Does the change make one zone know another's secret: a project's note key, seat name, command or policy in plugin text, or a host feature outside host integration?
4. **Restriction question** (a new guard or prohibition only). Name the harm, and check it is enforced where the facts are visible ([enforcement-map.md](enforcement-map.md)). A prohibition that should be a placement is a move, not a rule.
5. **Channel tests.** Swap: would it still hold under another output style? Then it is not stance. Every turn: is it needed on every turn? If not, keep it out of always-on channels. Enforcement: can advice not prevent the harm? Then it needs a hook, setting or server gate, and the prose copy goes. Owner: can the right owner change it where it sits? Duplication: is it said in two channels? Keep one, point from the other.
6. **One concept, one kind of statement.** A sentence that says what good work is belongs to an engineering skill, how to use the tools to a mechanics skill, what one tool does to the tool contract, which phases, notes and seats exist to the schema, a short must-do to a rule, and when something is hinted or refused to a hook ([0018](decisions/0018-content-placement.md)).
