Settled since v18

Decisions the owner settled after version 18

  1. Certainty dial is judgement, not config. It is settled in conversation through questions and answers, from the user’s or the agent’s domain knowledge; its outcomes are recorded as a ruling, an assumption on the node or an acceptance grant, and a project’s human-only decision classes are its limits.
  2. Acceptance is a server gate, opt-in per type (as the review phase is), satisfied the same way on every surface; a grant before the work, in the user’s own words, is a conditional grant that applies only when the accept card’s checks pass. The smallest gate shape is still open.
  3. Setup applies one tested template. It checks the connected tool profile, asks the domain and two to four questions with defaults, applies one CI-tested template with its steering, records the template and version, and leaves the user’s edits alone on upgrade; templates are never composed live.
  4. Two supported domains. Software development (primary) and keeping a knowledge base (first-class, on the knowledge tool profile); intake and operations is dropped.
  5. The knowledge journey constrains the other entry skills: learn, board, capture and plan mode each respect it (the list under Framing).
  6. The next contract stays as decided in call 7; further next proposals are held.

What no entry skill may break in a knowledge base

  1. No hook gives a knowledge session sizing tiers, a model table, dispatch rules, run-wave routing or “materialise before implement”.
  2. Plan mode in a knowledge session never orders materialisation or implementation dispatch.
  3. A hook names only selects and ops the session’s profile serves, or says nothing.
  4. Setup checks which profile it is connected to first; a missing context or runs_read never means the server is 3.x.
  5. Setup registers no director entry for a user who asked only for a knowledge base.
  6. A root whose declared types are all lifecycle: none gets no bundled build rules, and process rule documents never show as knowledge hits.
  7. No lifecycle-free item is listed or counted as queue, backlog, next or stalled work.
  8. No skill defaults to a blocks edge when either end is lifecycle-free.
  9. Capture, the board and dependency handling offer no bug, feature, tech-debt, blocker or backlog framing on a root whose types are all lifecycle-free.
  10. The knowledge journey runs end to end on the knowledge profile alone, with config delivered over REST.
  11. Nothing deletes an entry or a page without the user’s explicit yes; pruning prefers archive or a tag.
  12. No new phase, gate, seat, decision class or detector is added to serve this journey.
  13. Knowledge terms in the glossary stay method-neutral and borrow no build words.
  14. The knowledge profile keeps serving no advance and no runs; type discovery is fixed by a read of declared types, not the config tool.

Interfaces

What each skill reads and writes on the server

The skills were mapped against current/docs/api-reference.md (the generated tool contract) and the decision view source. Two facts shape everything here. The orchestration profile cannot read, answer, acknowledge or resume decisions, and cannot run reports. The director profile has no schema, config, document, note or write access. The tree's node types and goal notes are not on the server: they are schema config, pushed per root before a skill can write them.

No methodology words in the plugin. Charter, epic, story, increment and open question are one project's schema vocabulary (item types and note templates), not Task Orchestrator concepts. This plan speaks of nodes, the tree, a node's goal note, the work-item graph and items that build nothing. Any node with a goal note can be accepted. An incremental-delivery pattern that uses those words belongs in the manage-schemas pattern library (follow-up, not done).

Target interfaces

Decisions taken, and the server changes that remain

Decided in review

  • A decision stays a server record. It carries authority rules (class and credential), options with a recommended pick, severity and expiry, it blocks the item that asked, and it has server-raised classes that pause runs. Turning it into an item would rebuild all of that as transition gates.
  • A planned question is an item that builds nothing (builds: false), which next reads. A pattern may mark it with a trait such as open-question; that trait is pattern-library config, not tool behaviour. When it is ready to settle, the agent raises a decision on it. Answering it writes the ruling note and completes the item, which releases its blocks edges.
  • stdio is deprecated. Its limits (no human-only answers, no provable "user decided") are accepted. Enforcement happens over HTTP with a human credential.
  • Accept needs no server extension. Superseded since v18: acceptance is a server gate, opt-in per type as the review phase is. Every surface satisfies it the same way: plan-mode approval or a plain yes in Claude, or a skill on a harness with no plan mode. A grant before the work, in the user’s own words, is a conditional grant (calls 11 and 12). Sending back still uses the existing fix cycle.
  • The director runs on the orchestrator's tools (option C). Today director mode uses two connections: the orchestration connection, and the director profile for the decision reads and ops and for pause, resume and reissue, which are served there only. One connection is the destination, in 0003: the decision tools on every profile that needs them, with authority from the class and the credential (0002 records the interim state). Altitude is enforced in one place, the director-guard hook. It denies body reads and edits, and allows read-only scripts and background dispatch. The director profile stays served but is optional, and the hardened director agent is no longer the default. The director offloads research to background agents and answers from their concise result.

Principles

  • Organise interfaces by domain object (work, decision, board), not by skill.
  • Authority comes from the decision class and the credential. A profile only limits how much body text a caller can read.
  • The server computes the states skills keep asking about: refined, delegated, escalated, deferred.
  • Everything a skill produces links back to its source: a finding, a node's goal note or a ruling.
#Server changeShapeFor

Dropped after review: an acceptance decision class, a send-back trigger, human identity on stdio, and a deferred block reason (deferring moves a node to a later container, a pattern choice). Since v18 acceptance is an opt-in server gate; whether an answered decision of the right class is what satisfies it is open (see Still open).

Below the entries

What the agent runs on its own

Model-only user-invocable: false

  • Capturing work ("track this"): create-item becomes internal and is called by shape and by the agent whenever it notices something. On a root whose types are all lifecycle-free it captures an entry, never a bug or a feature.
  • Sizing and dispatch: orchestrate, model-effort, schema-workflow.
  • Moving work: status-progression, dependency-manager, batch-complete.
  • Plan hooks: pre-plan-workflow, post-plan-workflow.
  • Retrospective: session-retrospective, dispatched by a hook once its nudge text stops addressing the user.
  • Seat craft: planning-standards, designing-modules, implementation-standards, test-authoring, review-method, writing-documentation, defining-project-terms.

Expert overrides callable, not a way in

  • run-wave: resume a run by hand or launch a wave by hand.
  • ralph: an unattended queue drain, until standing work is modelled.
  • auditing-codebase, auditing-documentation: a cheap single pass, and the method audit uses for each slice.
  • init, configure-server: the steps start calls, kept for a deliberate re-run.

Still open

  • How accept hands approval to the project's ship step (merge, release) without naming a project skill.
  • The smallest acceptance gate: a required acceptance note satisfied only by an answered decision of the right class, or a new lifecycle step.
  • Whether board's hand-to-director instructions are a new config section or decision-class fields.
  • In director mode the hardened director agent has only the director profile, so learn, shape, accept, tune, start and audit must run through a background agent on the orchestration entry.
