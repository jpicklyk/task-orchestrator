Strategic Journey Map

The development journeys turned out to be one loop, and a knowledge base runs a lighter version of it. You intend, decide, accept and improve, and you look at where things stand whenever you need to. At any point you can learn the system from an agent that knows your own setup. The agent handles everything between those moments. The journeys only differ in where three dials are set (scope, certainty, autonomy) and in what the loop is pointed at: the product, its defects, or the process itself.

The loop at every level

Discovery: the moments repeat at every node

Work is a tree. A top node holds the goal, the nodes below it are pieces that can each be accepted on their own, and under each sits its work-item graph. The same moments run at every node, so exploring a design needs no new concept: a spike is Intend, Decide and Accept on a small node. For example, an incremental-delivery schema calls these levels epic and story, and the goal note a charter; the tool itself names none of them.

Decide settles a question three ways

  • Ask: a decision, answered by you or by the director.
  • Research: a background agent returns a concise finding.
  • Build: a small node builds to learn. The agent judges what is thrown away and what is refined toward the parent.

A ruling reshapes the levels below

  • What Decide settles at one node can rewrite, split, reparent or cancel the nodes and graphs under it. Reparent and a cancelling complete_tree exist today.
  • An item that builds nothing (builds: false) blocks the items it gates until it is ruled, and a build seat never picks it up.

Nodes show current state

  • No history machinery. A node's content lists the decisions that shaped it; the decision records on the server keep their own trail.
  • Refined means a node's required queue-phase notes are filled: enough to start, never locked.
  • Any node with a goal note can be accepted, judged against its own notes and rulings.

Who answers depends on your session mode

A seat or the orchestrator raises a decision. You or the director answer it, as the decision class allows. The orchestrator never answers, and the director never drives. Answer authority comes from the decision class and the caller's credential, never from the role or the profile.

Where each current skill goes

Config, not skills

The schema defines the journey

Methodology words belong to a schema, not to the tool. With no such config, work is plain items in the graph. incremental-delivery is one opt-in example profile under manage-schemas profiles/, never in the shipped default; the rows below are its own vocabulary. The entry skills read whatever the schema declares and hard-code no type or note name.

ItemWhere it lives

A node's content: internal or referenced

  • Internal (no storage config): the content lives in the node's notes.
  • Referenced: a schema can keep content outside, in markdown files in the repo, Jira or Linear. Items stay sparse, with a short note that references the source, and a skill bound in the schema (a note's skill: or a seat's skills:) writes it.
  • Task Orchestrator never syncs with the outside source or reads it back.
  • Decision records follow the same pattern later, as an adapter off decision.* events. Nothing is built for it now.
Before changing anything

Constraints and corrections

Layer rules, settled in GLOSSARY.md and decisions 0001 and 0002

  • The orchestrator records your answer, never its own, through role-neutral decisions_write with your words verbatim.
  • The director answering on its own still contradicts director/SKILL.md. That's reshaping work: per-class autonomy moves into config.
  • Steering is the new name for the hook config orchestration.mode, so "orchestration mode" now names only the session mode.
  • The board is your view, not the director's session. This reverses an earlier reviewer ruling that the director session is the board. The director acts on the board at your instruction.

Mechanics of demotion

  • user-invocable: false hides a skill from the slash menu, but the Skill tool can still reach it.
  • disable-model-invocation: true means only the user can run it. Merging review-proposals means dropping that flag.
  • Hook and skill text tells the user to type /session-retrospective, /director, /configure-server and /init. Fix those strings first.

Corrections from verification

  • The server already streams decision.raised and decision.answered over SSE. The wake-up gap is in the plugin.
  • report rollup already returns cost (director profile only).
  • Plan approval already starts the build, but all or nothing: one unrefined leaf sends the whole plan to hand dispatch.
  • Review has no send-back trigger, and reopen works only from terminal.
