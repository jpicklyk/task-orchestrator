Journey Config Fit

Can a project's configuration express what each of the eight user journeys needs: seven for software development, one for keeping a knowledge base? Every journey stage was turned into a statement of what the config must be able to say, then graded against the config language as it is today. A critic re-checked each grade against source, a designer wrote one real config per development journey, and a third pass worked the knowledge base through the knowledge endpoint to find where the development design leaks into it.

Sources: the Strategic Journey Map (v11), a catalogue of the config model built from config.schema.json, the parser and the plugin hooks, and the working files for requirements, fit, critique, sketches and the knowledge base, kept in design/evidence/. Grades below are reconciled across every pass.

The short answer

The config language carries most of the journeys already. Half of what looked missing exists under another mechanism, and a third of the requirements were never config questions at all. Seven real gaps remain. Five come from the development journeys, each with a working mechanism today that falls short. Two come from the knowledge base: a root cannot say what it is, and the note and link model still speaks the language of building. The certainty dial moved out of the list: it is judgement, held in conversation, not something a project declares.

How setup chooses a config

A reference library, a few questions, one template

Setup holds a library of templates and the use cases each supports. It asks a few questions, picks the template that fits and applies it. Most of the library exists: manage-schemas has ten workflow profiles, several outside software (a research pipeline, content production, support triage, document review), and a classifier that picks between them. Setup does not call it yet.

1. Domain first

Building software, research and knowledge, content, or support and operations. The domain decides which follow-up questions make sense and which templates are candidates. A personal knowledge system never sees a question about reviewers or test authors.

2. Then how much structure

Within a domain: a base template, plus add-ons such as an acceptance gate, independent review, question and probe items, or background agents. Questions and probes are add-ons for any domain, since uncertainty is judgement, not a kind of project.

3. Questions about the work

Two to four, each with a default, so "I don't know" still lands somewhere working:

  • Do you want to approve results before they close?
  • Will background agents work in parallel?
  • Do you usually know the whole scope up front?

What makes it hold up over time

  • Steering is part of the template. The hooks are written for software (sizing by file count, an implementer seat, a model table). A knowledge template sets steering to schema or off, or the hooks push software process onto note-taking.
  • Templates ship pre-built and tested, not composed live. Each supported combination is a finished template validated in CI. Add-ons are only the few traits designed to combine safely, because of the traps below.
  • Setup records the template it applied, and its version. That record is what "stay current" compares against when the plugin changes (gap 5).
  • Upgrades leave the user's edits alone. The bundled-rules policy already does this: a copy matching a known old version is replaced, a customised copy is left and reported. Templates reuse it per type and per rule.
  • Picking is the easy part. The ongoing cost is keeping templates correct as the plugin changes and merging upgrades into edited configs. Templates that need an open gap ship with today's workaround.

The knowledge-base template

work_item_schemas:
  topic:                     # a grouping; may nest
    lifecycle: none
    notes: [ { key: scope, role: queue, maxLength: 800 } ]
  entry:                     # one idea, in the user's words
    lifecycle: none
    notes:
      - { key: content,   role: queue, maxLength: 3000 }
      - { key: source,    role: queue, maxLength: 600 }
      - { key: relations, role: queue, maxLength: 1200 }  # gap 7
  source:                    # an article, book or paper
    lifecycle: none
    notes: [ { key: summary, role: queue, maxLength: 2500 } ]
note_limits: { mode: reject }
extensions:
  claude-code:
    orchestration: { mode: off }   # gap 6: session start still speaks
    retrospective: { mode: off }

On a knowledge connection setup registers only the knowledge entry, skips the director entry, creates a lifecycle-free anchor and pushes the config over REST, since the knowledge endpoint serves no config tool. Long-form synthesis is a versioned page document.

Key names such as goal, intent or question belong to a template, not to Task Orchestrator. A method that prefers epic or story uses those names instead.

Found by writing real YAML

Composition traps

None of these is a missing feature. Each makes a correct-looking config behave wrongly. They are why setup applies pre-built, tested templates instead of composing blocks for users who never read the config.

  • A trait that adds a seat makes the type seat-aware. Every unseated required note on it becomes unowned, and run-wave then excludes the item.
  • A declared seat rules list replaces the defaults. Adding one project rule means listing the plugin defaults again.
  • A forceUp or forceDown list in tier-policy replaces the plugin's whole list.
  • A per-root copy of a floor type replaces it whole and stops receiving floor updates.
  • An auto parent closes when its children do, so a retrospective "per accepted node" fires before the user accepts unless the node is manual or carries a required acceptance note.
Guard rails from the knowledge base

What the development design must not break

Development stays the design centre. These are the rules it must keep so a knowledge base keeps working, each traced to a leak found on the knowledge endpoint.

  1. A knowledge session gets no sizing tiers, model table, dispatch rules, run-wave routing or "materialize before implement" from any hook.
  2. Plan mode in a knowledge session never orders materialisation or implementation.
  3. A hook names only what the session's profile serves, or stays silent.
  4. Setup checks which profile it is connected to before reading a missing call as an old server.
  5. Setup registers no director entry for a user who asked only for a knowledge base.
  6. A root whose declared types are all lifecycle: none gets no bundled build rules, and process rules never appear as knowledge hits.
  7. No lifecycle-free item is ever listed or counted as queue, backlog, next or stalled work.
  8. No skill picks a blocking edge by default when either end is lifecycle-free.
  9. Capture, the board and dependency help offer no bug, feature, tech-debt, blocker or backlog framing on a root whose types are all lifecycle-free.
  10. The knowledge journey runs end to end on the knowledge endpoint alone, with config delivered over REST.
  11. Nothing deletes an entry or a page without the user's explicit yes; pruning prefers archive or a tag.
  12. No new phase, gate, seat, decision class or detector is added to serve this journey.
  13. Knowledge terms in the glossary stay method-neutral and borrow no build words.
  14. The knowledge endpoint keeps serving no advance and no runs. A client that needs its own types gets a read of declared types, not the config tool.
Belongs elsewhere

Follow-ups that are not config

  • Setup uses the profile library, gains a light template, a knowledge-base template and a domain question, checks the connected profile first, and records what it applied (R21, R22, R46).
  • Knowledge-shaped skills: capture that follows the template's types, a revisit digest in place of the board, and learn that explains the applied template (journey 8).
  • Glossary: the opening line and Building item frame the tool as building; Lifecycle-free item and Link are candidate entries (glossary-alignment backlog).
  • Note purposes for the parts a method-neutral skill needs, in place of part skills: a project marks its goal, finding and ruling notes with the note entry's purpose, which the server parses and serves, and the acceptance basis travels as evidence on the acceptance decision (0015, R24). Not built yet.
  • Director standing instructions live in the project's own instructions, which a director session loads (R13).
  • Attention outside runs is the board skill's reading, not a threshold in config (R26).
  • Which config change a proposal adopted is a link the tool records, as it already links plan documents to items (R20).
For our review

Questions to settle

  1. Settled: the certainty dial is judgement. It stays in conversation, clarified through questions; its outcomes are recorded, and human-only classes set its limits.
  2. Settled: acceptance becomes a gate in the server, satisfied the same way by every surface, with approval before the work as a conditional grant.
  3. Settled: setup selects from a reference library, domain first, with templates shipped pre-built and tested.
  4. Settled: two domains. Software development is primary; keeping a knowledge base is first class, on the knowledge endpoint. Intake and operations is dropped.
  5. Open: is "a note satisfied only by an answered decision" the right smallest gate? The alternative is a new acceptance step in the lifecycle, which costs more and touches every schema.
