- `fixtures/repo-config.yaml` - seat-less snapshot of this repo's tracked `.taskorchestrator/config.yaml`
  as of base `f9d71a69` (the per-root layer pushed to the fixture root).
- `fixtures/global-config.yaml` - snapshot of `deploy/global-config/.taskorchestrator/config.yaml` as of
  base `f9d71a69` (the global process-schema floor layer).

These are loaded from the test classpath at runtime rather than read from their live repo paths, so
the test does not depend on the working directory a future `gradlew` invocation happens to use.
They are intentionally NOT kept in sync with the live files: drift is expected, and the live files
must NOT be re-copied here, because that would bring in seats and by-seat dispatch and change the
goldens. Validity of the live files is guarded separately by `LiveConfigFilesParseTest`.

## Recording

PowerShell, from the worktree root:

```powershell
$env:A1_GOLDEN_RECORD = "true"
& .\gradlew.bat ":current:test" "--tests" "io.github.jpicklyk.mcptask.current.interfaces.mcp.SeatlessResponseGoldenTest"
Remove-Item Env:\A1_GOLDEN_RECORD
```

Every test FAILS on a record run by design (message: `"recorded golden '<name>' ... re-run WITHOUT
A1_GOLDEN_RECORD to verify"`) — a record run can never read as a silent pass. Re-run the identical
command with the environment variable unset afterward to verify the newly recorded goldens compare
clean.

**Note on the trigger mechanism** (flagged for reviewer confirmation): the T0 dispatch specified a
JVM system property (`a1.golden.record=true`). `current/build.gradle.kts`'s `tasks.test { }` block
(read by the test author, not edited — outside T0's writable File-ownership scope) forwards no `-D`
system property from the `gradlew` command line into the forked test worker JVM; only
`user.timezone` is explicitly forwarded via `systemProperty(...)`. Gradle's `Test` task DOES inherit
the launching process's environment into the forked worker by default, with no build-file change
required, so the test reads the environment variable `A1_GOLDEN_RECORD` instead of a system
property. This is a self-resolved ambiguity per the test-author protocol's carve-out (evidence:
`current/build.gradle.kts`'s `tasks.test` block); the reviewer should confirm this reasoning holds,
or ask for a `build.gradle.kts` change to wire the literal system property if system-property parity
is actually required.

Per the dispatch contract, the T0 test author does not run `:current:test` — recording and
full-suite verification are orchestrator-run.
